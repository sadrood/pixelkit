### 3. 预热缓存（找空闲时段）

> ⚠️ **这一步会吃满账号 RPM（约 5~6 次/分钟），全站 AI 会一起排队**——
> 包括 AI 助手对话、结算散文、开局批注、墓志铭。
> 建议**夜里跑**；或者用下面的 `--gap 20000` 留一半额度给线上。

> ⚠️ **必须打「跑着这份代码的那个进程」**。缓存活的是 `server.js` 的进程内存，
> 在开发机本地跑只会暖本地那份文件，**3002 / 8081 上依然是空的**。

**在服务器上跑**（推荐 SSH 进服务器，两条命令选一条）：

```bash
ssh root@139.9.176.191
cd /opt/pixelkit-test                  # 实测路径，见上面的「服务器实况」
tmux new -s warm                       # 挂后台，断线不中断

# ① 打测试自己的 3002（最直白；暖和的就是 3002 那份缓存）
BOOK_AI_URL=http://127.0.0.1:3002/api/agent/book-ai \
  node docs/人生之书/tools/warm-rewrite-cache.cjs

# ② 或打服务器本机的 3001（那是**生产的进程**，暖出来的是生产那份缓存；
#    本次目标是测试环境，别用这条）
```

**也可以从本机跑、指向测试环境**——注意：**暖的仍是服务器上那个进程的缓存，
本机不会留下任何东西**，所以两条路对结果等价，只是在本机跑容易误以为在暖本机：

```bash
BOOK_AI_URL=http://139.9.176.191:3002/api/agent/book-ai \
  node docs/人生之书/tools/warm-rewrite-cache.cjs
```

> 只有当 3002 的登录被重新打开（服务器 `.env` 里设了 `TEST_AUTH_USER`）时，
> 才需要加 `BOOK_AI_AUTH=<用户>:<密码>`；脚本开头的连通性预检会先探一次门，
> 撞上 401 会立刻退出并提示，不会闷头跑完 1087 条才报错。

常用开关：`--gap 20000`（留余量给线上）、`--limit 20`（先冒烟）、
`--dry`（只统计条数，不发请求）。**放全量前务必先 `--limit 20` 看一眼。**

**外加一类：AI「另一种可能」（v2.6 新增）**
结局页的反事实也是同一张缓存表，键 = `世界线 + 那次抉择 + 结局`，与玩家无关。
键空间约 **3150 条**（42 抉择 × 15 结局 × 5 线），全量要 10 小时以上，所以脚本
默认**用模拟采样**只取真实出现频率最高的那批：

```bash
node docs/人生之书/tools/warm-rewrite-cache.cjs --dry --alt          # 先看条数
node docs/人生之书/tools/warm-rewrite-cache.cjs --alt --gap 18000    # 结果改写 + 反事实
node docs/人生之书/tools/warm-rewrite-cache.cjs --only-alt --limit 60 # 只跑反事实的前 60 条
# 采样强度：--alt-runs 60（每条线模拟几局）｜取多少条：--alt-max 260（0 = 不限）
```

实测（1500 局模拟）：分岔口高度集中在**第三章**（五线各 4% 左右），
要覆盖 80% 的分岔口需要 36 个 (线,章) 组合、约 1920 条——所以别一次吃完，
**分批跑**：先 `--alt-max 60`，观察几天命中率再决定加不加。

**速度口径**：单条请求约 14s（模型生成十几秒），加上 `--gap` 才是墙钟时间。
排期一律按 **22~23s/条**（16s 间隔 + 生成）——详见下面「全量预热完成记录」一节，
那里有 1087 条全量跑的实测（6.7 小时）。

**命中验证怎么做**（预热完必须做，否则不知道暖对没暖对）：
从 `data/book-rewrite-cache.json` 里取一条 `book-alt` 的键，按不可见分隔符拆成
`[世界线, 抉择, 结局]` 原样再打一次 → 应返回 `cached:true`；
再换一个不存在的抉择 → 应 `cached:undefined` 且真生成。两条都成立才算键对上了。

### 补漏：用 `warm-topup.cjs`，别重跑全量

`warm-rewrite-cache.cjs` 是整程走一遍的，用它补 11 条要重走 1087 条（约 5 小时）。
补漏工具按**确定性采样重算键集 → 与缓存做差 → 只补缺失**：

```bash
cd /opt/pixelkit-test
BOOK_REPO=/opt/pixelkit-test BOOK_AI_URL=http://127.0.0.1:3002/api/agent/book-ai \
  node docs/人生之书/tools/warm-topup.cjs --dry         # 先看缺几条（本次 8 条）
BOOK_REPO=/opt/pixelkit-test BOOK_AI_URL=http://127.0.0.1:3002/api/agent/book-ai \
  node docs/人生之书/tools/warm-topup.cjs --gap 15000   # 补漏（几分钟）
```

本次实测：11 条缺失 → 首轮补上 3 条（余 8 条仍撞限流）→ 二轮全部补上 → **缺失 0 条**。

> 键集能对上的前提是**随机源固定**（两个工具都把 `Math.random` 换成种子 20260914 的 PRNG）。
> 若改了种子或采样参数（`--alt-runs` / `--alt-max`），两边必须同时改，否则差集会虚高。

规模：**208 条原文（含性别变体去重后）× 4 个角度 = 832 条**（内容增长后由 193 涨到 208；
其中 15 条是「年龄维度」新增的寿数抉择）。
另注：第 6 章有 5 个「函数体」选项写不出确定正文，脚本与客户端都会跳过——
那 5 处永远没有 AI 改写，是设计如此，不是漏跑。

**耗时（2026-09-14 已在服务器实测标定，别再估算）**：

标定跑法：`--gap 18000`，前台跑 10 分钟就停（Ctrl-C），看进度行的 `均 Xs/条`。

实测结果（2026-09-14 15:43–15:53，测试环境）：

```
进度 10/1087　新生成 5　命中缓存 5　失败 0　均 11.7s/条　剩余约 149 分钟
```

→ **全量 ≈ 2.5 小时**（`--gap 18000`）。附注：

- 该 10 分钟里 **0 失败**，说明限流并不总是发生；之前冒烟那次的高失败率是**我手工 curl
  在跟预热抢额度**造成的，属人为干扰，不代表常态。
- 上游 `429` 是**全账号**的：测试与生产两个进程都会刷
  `book-ai http 429`（见 `/root/.pm2/logs/pixelkit-{test,prod}-error.log`）。
  所以活人流量大的时段跑，ETA 会被拉长——**信进度行，不信估算**。
- 缓存命中率 50% 是因为标定前缀已经暖过；首次全量时「新生成」会一路涨。

一句判断标准：**标定 3 分钟就知道今天该不该放全量**——`均 Xs/条` × 剩余条数 = 真实 ETA。

**幂等可续跑，但续跑不省时间**：已进缓存的会由服务端秒回、不消耗上游额度，
可是脚本对每条都要 sleep 一次间隔，**中断后重跑仍要整程走完 1087 条**，只是不再烧额度。

### 4. 确认缓存生效

```bash
# pm2 在非交互 SSH 里通常不在 PATH，直接读日志文件最稳：
grep book-rewrite /root/.pm2/logs/pixelkit-test-out.log | tail -3

```

⚠️ `/root/.pm2/logs/` 里同时存在 `pixelkit-server-*`、`pixelkit-prod-*`、`pixelkit-*` 等旧日志，
**别抓错文件**：测试环境看 `pixelkit-test-*`，生产看 `pixelkit-prod-*`。

注意区分：`缓存已载入 N 条` 是**服务启动时**打的。预热是另一个进程在跑，
它只会让这个 N 在下次重启后才变大——**不要拿这条日志判断预热进度**，
看预热脚本自己的 `进度 x/1087　新生成 ...` 行。

## 关键事实（容易搞错的）

1. **预热必须在服务器上跑**（或指向服务器）。
   缓存活的是 `server.js` 的**进程内存**，落盘文件只是重启恢复用。
   在本机跑只会暖本机那份文件，**生产/测试的缓存还是空的**。

2. **两种「打不通」，症状完全不同**：
   - 接口要 Basic Auth 而脚本没带（只在有人把测试环境登录重新打开时才会遇到）→
     401 的纯文本响应，`JSON.parse` 直接抛异常。旧版脚本会把它当成「请求异常」
     重试三次再记失败——1087 条就是 6~7 小时白跑。
     现版本会**在开头的连通性预检里就拦住**，立即退出（退出码 2）并提示加凭证。
   - 打 3001 但那个端口上没有跑这份代码 → 连接被拒，同样是「请求异常」，
     预检会打一行 `⚠️ 连通性预检异常` 提醒你。
   **跑之前先 `--limit 20` 冒烟，看「新生成」在涨、失败是 0，再放全量。**

3. **测试环境的登录默认已关闭**（2026-09-14）。
   `server.js` 里那段 Basic Auth 现在是「设了 `TEST_AUTH_USER` 才启用」。
   但**真正的开关在服务器的 `/opt/pixelkit-test/.env`**（第 16–17 行原本写着
   `TEST_AUTH_USER=pixelkit` / `TEST_AUTH_PASS=...`，已删除；备份在
   `/opt/pixelkit-test/.env.bak-20260914-155925`）。
   想重新把门关上：把这两行加回 `.env` → `pm2 restart pixelkit-test --update-env`。
   实测四种状态都验过：无变量→200；设了→无凭证 401 / 带凭证 200。

   ⚠️ **改这里会连带影响部署 hook**：`/home/pixelkit/pixelkit.git/hooks/post-receive`
   的健康检查会从 `.env` 读这对凭证去 curl `/api/fileshare/list`。
   原逻辑在 `.env` 里没有该变量时会 fallback 成老默认密码，导致部署时报
   「健康检查失败」。已同步改成「有凭证才发 Basic Auth，没有就不发」
   （hook 备份：`post-receive.bak-20260914-155925`）。

   关掉登录意味着**谁都能从公网打 3002**，而它跟生产共用同一套上游 Key——
   真在意的话，在 nginx / 安全组上按 IP 放行，比 Basic Auth 更合适。

3. **`data/` 会跨部署保留**——`deploy.sh` 已约定上传必须排除 `data/`，所以
   `data/book-rewrite-cache.json` 不会被冲掉。
   （例外：如果你手动 `rm -rf data/*` 或重装服务器，1087 条要重跑。）

4. **顺序不能反**：先部署代码、再预热。反了的话服务器上没有 `book-rewrite` 接口，全部失败。

5. **PM2 重启会清空进程内存**，但启动时会把 json 重新载入 → 中途重启不丢已生成的部分。

6. 缓存路径可以用 `BOOK_RW_CACHE_FILE` 环境变量覆盖。默认
   `data/book-rewrite-cache.json`。

7. 想调切入角度：改 **`docs/人生之书/tools/split.cjs` 里的 `AI_RW_ANGLES`**
   （这才是生成页的真相源；`split.cjs` 会整段覆盖母本的 AI 层），
   **同时改 `warm-rewrite-cache.cjs` 里的 `ANGLES`**，否则缓存键对不上、预热全落空。
   原因：服务端按 `angle + '\0' + canon` 做键（`server.js` 里的 `cacheKey`），
   而 `angle` 就是这两处数组里的那个字面量——**任何一边改了文字就全量失配**。
